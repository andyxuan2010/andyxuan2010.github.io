# 企业消息传递 - Azure Service Bus

> **简要决定：** 使用 Service Bus 进行持久的业务工作和命令。使消费者幂等，定义死信恢复，并且不将代理视为日志系统。

## 目的

此体系结构使用 Azure Service Bus 作为业务消息的企业代理，这些消息必须能够承受临时生产者或消费者中断、吸收工作负载峰值并保持独立系统之间的受控切换。它支持队列的点对点处理以及主题和订阅的发布/订阅扇出。

典型的消息包括采购订单、付款指令、预配请求、清单更新、装运命令和工作流程状态更改。生产者提交契约定义的消息并独立继续；消费者根据自己的能力和可用性来检索、处理和结算消息。

Service Bus 是消息传递代理，而不是业务工作流引擎或日志系统。生产者或域服务对于业务状态仍然具有权威性。消费者 MUST 是幂等的；当结果比消息保留更重要时，消费者 MUST 在代理外部保留其业务结果或可审计的处理日志。

## 范围和设计成果

当工作负载需要执行以下操作时，请使用此模型：

- 在时间和可用性上将生产者与消费者分离；
- 在竞争的消费者之间分配独立的工作；
- 向多个由不同团队负责的订阅者发布一条业务消息；
- 将毒消息或无法处理的消息路由到死信队列进行调查；
- 当客户端不确定发送是否成功时，防止意外重复发送；
- 安排消息以供将来处理；
- 通过会话保留相关消息的处理顺序；
- 在支持的事务边界内发送结果消息时原子地接收和结算消息；或
- 缓冲间歇性需求，以便下游服务能够以安全的速率进行处理。

目标结果是：

- 每个队列、主题和订阅都有一个所有者、目的、模式、保留和支持路径；
- 消息对于业务恢复目标来说足够持久，并携带相关性和幂等性数据；
- 消费者可以重试暂时性故障，而不会创建无限制的毒消息循环；
- 死信消息是可见的、可处置的并且可通过受控程序恢复；
- 工作负载峰值和临时下游中断会产生有限的积压，而不是同步故障级联；
- 有序处理仅应用于需要它的业务密钥；和
- 消息健康状况、期限、积压、交付尝试和结算失败都是可监控的。

## 背景和决策驱动因素

同步调用将调用者的可用性和延迟与每个下游依赖项结合起来。必须等待不可用的付款、预配或清单服务的生产者可能会超时、重试相同的操作或失败面向用户的请求，即使工作稍后可以安全完成。

该决定的驱动因素是：

- **可靠性：** 高价值的业务消息不能仅仅因为消费者在一段时间内不可用而丢失。
- **时间解耦：** 生产者和消费者不需要同时在线或进行相同的扩展。
- **负载均衡：** 流量突发应该成为可观测到的积压，工作进程可以按受控速率排空。
- **扇出：** 多个消费者可能独立需要一份业务事件的副本，而生产者无需为每个消费者管理一个队列。
- **故障隔离：** 单个格式错误或重复失败的消息不得无限期地阻止不相关的工作。
- **排序和关联：**相关消息可能需要有序处理或共享会话密钥，而不对整个工作负载强加全局排序。
- **可审计性：** 消息身份、生产者、消费者、结果和重试历史记录必须支持协调事件调查。
- **安全性：** 消息数据、凭据、网络路径和管理操作需要显式所有权和最低权限。

## 考虑的选项

### 同步 API 调用

当调用者需要立即响应、请求验证或同步读取时，请使用 API。当下游服务暂时不可用或者工作时间可能超过调用者的请求预算时，API 并不是持久业务命令的糟糕替代品。 [API 主导的集成 - Azure API Management](api-led-integration-azure-api-management.md)定义了相应的受控 API Front Door 模式。

### Azure Event Grid

使用 Event Grid 进行面向通知的事件传递，尤其是当 Azure 资源更改或应用事件应通知订阅者而不需要代理功能（例如会话、事务或死信驱动的工作恢复）时。Event Grid 和 Service Bus MAY 一起使用：Event Grid 可以通知，而 Service Bus 承载需要持久处理语义的高价值工作。

### Azure Event Hubs 或其他流平台

使用 Event Hubs、Kafka 或等效的流平台来实现极高吞吐量的遥测、面向追加的流和独立的消费者偏移。不要仅仅因为有效负载称为事件而选择流。需要队列结算、死信处理、会话或代理事务的业务命令属于消息代理（例如 Service Bus）。

### Azure Storage 队列
存储队列应用于具有较简单交付要求的简单、大容量工作队列。当工作负载需要主题和订阅、消息会话、重复检测、事务、高级代理语义或企业级消息治理时，请选择 Service Bus。

### 选择方向：Azure Service Bus

将 Service Bus 用于需要持久代理存储、点对点或发布/订阅路由、受控重试、死信队列、重复检测、计划传送、有序会话或事务消息传递的业务消息。将域服务、工作流运行时和日志系统保留在代理之外。使用 Logic Apps、Functions、容器或 App Service 在收到消息后执行业务行为。

![使用 Azure Service Bus 的企业消息传递架构](../../assets/service-bus-enterprise-messaging-architecture.svg)

生产者向队列或主题提交消息，并不直接调用每个消费者。队列一次给予一个成功的消费者对一条消息的所有权。主题为每个匹配的订阅创建一个独立的副本，允许消费者独立扩展和失败。业务结果持久化记录后，消费者进行消息结算；失败会在有界策略内重试，并最终移至相关的死信队列。

命名空间是逻辑容量和安全边界，不能替代工作负载所有权。当隔离、数据驻留、网络暴露、生命周期或嘈杂邻居风险需要时，分离命名空间或实体。不要仅仅因为不相关的关键工作负载共享一个客户端库而将它们放入同一个命名空间中。

## 实体选择

### 点对点工作的队列

当一个消费者或一个竞争消费者池应该处理每条消息时，请使用队列。典型用途包括：

- 采购订单履行；
- 支付指令处理；
- 资源预配请求；
- 清单核对工作；
- 文件或批处理；和
- 发送给单一受限能力的命令。

当工作独立且可以安全地同时处理时，可以横向扩展消费者。消费者 MUST 仅在完成所需的持久工作或记录安全、幂等的结果后才结算消息。失败或放弃的消息必须保持有资格重试，而不是默默地确认。

### 发布/订阅的主题和订阅

当一个发布者应通知多个由不同团队负责的消费者时，请使用主题。每个订阅都充当订阅者副本的持久虚拟队列。当业务路由规则可以表示为稳定的消息属性时，使用订阅过滤器可以避免将每条消息发送给每个消费者。

示例包括独立传递给履行、清单、财务和分析订阅的 `PurchaseOrderSubmitted` 消息。发布者不得假设所有订阅者同时或以相同的顺序处理消息。每个订阅者都负责自己的检查点、重试、死信和协调过程。
不要使用主题来替代共享数据库或全局事务协调器。订阅者可能会被延迟、重试、暂时不可用或永久退休；域契约必须定义这些状态如何影响源业务流程。

### 死信队列

每个生产队列和订阅 MUST 有记录在案的死信策略。死信是一种操作状态，而不是消息删除。消息可能是死信的，因为传递尝试超出了配置的限制、消息无法传递、应用了过滤器或过期条件，或者消费者明确拒绝它。

死信进程应该：

- 保留原始消息 ID、相关 ID、实体、传递计数和失败原因；
- 对计数、年龄、费率和业务关键性发出告警，而不仅仅是对非零数量发出告警；
- 将暂时的依赖失败与畸形的契约或永久的业务拒绝分开；
- 在检查和再处理过程中保护敏感有效载荷；
- 需要授权操作员或批准的重播工作流程才能重新提交；和
- 记录邮件是否被更正、重播、隔离、协调或永久拒绝。

切勿创建自动无限死信重播循环。重播必须有一个新的尝试边界、一个原因、一个有界速率以及一种安全停止的方法。

### 重复检测和幂等性

当生产者可以安全地提供稳定的消息 ID 并且重复发送代表相同的业务意图时，启用重复检测。当客户端在不确定的网络结果后重试时，这可以减少重复的代理条目。检测窗口和身份字段必须与业务重试范围相匹配。

重复检测不提供端到端的一次性业务处理。消费者可能会在执行副作用后和消息结算前崩溃；代理可以再次传递消息。消费者 MUST 在应用不可重复的副作用之前使用幂等性密钥、收件箱记录、唯一业务约束或等效的重复数据删除机制。

幂等性记录应将消息身份绑定到操作、消费者版本、结果和相关业务密钥。至少将其保留一段时间，在此期间副本可以到达并且企业仍然可以重试或协调操作。

### 预定交付

使用计划消息进行延迟工作，例如续订尝试、付款重试、预留到期或计划的配置操作。将预期执行时间和原因存储在消息元数据或有效负载中，并使消费者容忍延迟交付，因为调度不是实时保证。

计划的工作应该有一个所有者、取消路径、时区策略、最大延迟和对帐流程。当专用调度或工作流服务更适合时，请勿使用大量计划消息作为无限制的通用调度程序。

### 会话和有序处理
当必须按顺序处理相关消息或消费者需要稳定的关联上下文来进行请求响应或工作流处理时，请使用会话。选择代表需要订购的最小业务流的会话 ID，例如订单 ID、账户 ID 或配置请求 ID。

会话不会跨队列或主题创建全局排序。它们可以减少热键的并发性，创建必须监视的锁定和所有权行为，并增加卡住会话的影响。消费者必须安全地释放或放弃会话所有权，并定义如何隔离和恢复会话中的毒消息。

如果消息不需要排序，则省略会话并更自由地扩展竞争消费者。当较窄的密钥就足够时，请勿序列化整个租户、区域或业务域。

### 事务消息传递

当支持的操作需要原子代理边界时，例如从一个实体接收消息并将结果消息发送到同一事务范围内的另一个实体，请使用 Service Bus 事务。保持交易简短，并避免在调用缓慢或不可靠的外部系统时持有代理锁。

Service Bus 事务不是跨任意数据库、HTTP 服务或 SaaS 平台的分布式事务。为了实现跨系统一致性，请使用发件箱、收件箱、幂等消费者、持久工作流程、补偿操作或协调流程。记录哪些操作是原子的以及哪些结果最终是一致的。

## 消息契约和处理生命周期

每条业务消息都应使用版本化信封，其中至少包含：

- `messageId`：用于追踪和去重的稳定身份；
- `messageType`：语义名称，例如`PurchaseOrderSubmitted`；
- `schemaVersion`：具有兼容性策略的契约版本；
- `correlationId`：业务流程或请求关联；
- `causationId`：导致此消息的消息或命令；
- `producer`：创建消息的服务和版本；
- `createdAt`：UTC 创建时间；
- `subject`或业务密钥：消息关注的实体或聚合；
- `tenant` 或应用的组织范围；
- `dataClassification`：处理和记录分类；
- `traceContext`：分布式跟踪传播数据；和
- `payload` 或对外部内容的声明检查引用。

当批准的加密存储和声明检查参考更安全时，请勿将大型文件、镜像或敏感文档直接放入邮件中。引用必须具有与消息生命周期匹配的所有者、保留策略、授权检查、完整性保护和删除行为。

正常的处理生命周期是：

1. 生产者验证命令或事件，创建消息标识，并将其发送到选定的队列或主题。
2. Broker 接受并存储消息；当业务工作流需要协调时，生产者记录接受的消息 ID。
3. 消费者在选定的锁或会话模型下接收消息并验证信封和模式。
4. 消费者检查幂等性状态，执行有界业务工作，并持久化记录结果。
5. 消费者仅在成功或明确记录持久化结果后才结算消息。
6. 瞬时故障导致有回退的有限重试；永久或反复失败的消息将移至死信队列。
7. 操作员在事件或恢复期间协调积压工作、死信消息、计划工作和业务状态。

## 业务消息示例

|留言 |实体|消费者行为|重要控制|

|采购订单已提交 |履行、清单和财务订阅主题 |每个域处理自己的副本并记录其结果 |相关 ID、模式版本、订阅过滤器、幂等消费者 |
|付款说明 |队列|支付工作进程处理该消息并调用支付提供商 |严格授权、去重、有限重试、审计日志、DLQ 审核 |
|预配请求 |具有按请求或资源 ID 键控的会话的队列 |工作进程按顺序执行步骤并发送状态消息 |会话 ID、超时、补偿、重试预算、操作所有权 |

## 安全和网络架构

将 Microsoft Entra 身份和 Azure RBAC 用于客户端和服务支持托管身份或工作负载身份联合的应用和操作员。分别划分发送、接收、侦听和管理权限的范围。共享访问签名 MAY 用于记录在案的兼容性要求，但密钥 MUST 作为机密存储、轮换、限定范围并进行审核。

对于敏感或内部消息：

- 当网络设计需要私有访问时，使用私有端点和经批准的私有 DNS；
- 将命名空间网络访问和管理操作限制为经批准的身份和路径；
- 在数据分类需要时对传输中的消息进行加密并配置客户管理的密钥；
- 避免将凭证、访问令牌或不必要的受监管数据放入消息正文或应用属性中；
- 对诊断和死信检查工具中的敏感内容进行脱敏；和
- 记录对命名空间、实体、授权、网络规则、策略和消息保留的更改。

消息平台本身并不授权该业务行为。在应用请求的更改之前，消费者必须验证生产者、消息契约、租户或资源范围以及当前业务授权。

## 弹性、吞吐量和成本
使用基于队列的负载均衡使临时中断和突发表现为积压而不是同步故障。定义可接受的队列寿命、最大积压、排空速率，以及生产者必须应用反压、拒绝工作或路由到业务异常路径的点。

容量规划必须包括消息大小、入口和出口速率、并发接收器、结算操作、会话热点、事务、重复检测窗口、保留、计划消息量、峰值恢复率和区域故障转移需求。如果消息很大或处理成本很高，消息计数较低的队列仍然会使工作负载饱和。

当吞吐量和隔离需要时，使用分区、多个实体或单独的命名空间。从工作负载的恢复目标、网络要求、吞吐量和支持模型中选择 Service Bus 层和可用性功能。异地复制或灾难恢复功能需要明确的数据丢失、故障转移、命名空间、DNS、凭证和重放决策；它们并没有消除消费者幂等性和业务协调的需要。

主要成本驱动因素是命名空间层和容量、消息操作、消息大小、保留、私有网络、遥测摄取、异地复制和消费者计算。不要无限期地保留死信有效负载，也不要在没有所有者和度量消费者需求的情况下创建主题订阅。

## 操作注意事项

API 或消息传递平台团队负责命名空间基线、网络集成、身份模型、层、配额、诊断设置、客户端标准和生命周期控制。领域团队负责实体定义、消息契约、消费者行为、幂等性、死信处理、SLO 和业务协调。

监控每个队列和订阅：

- 活动消息计数、计划消息计数和死信计数；
- 最旧的消息年龄和年龄百分位数；
- 入口、出口、完成、放弃、延迟和死信率；
- 交付计数、锁定丢失、结算失败、接收器错误和限制；
- 会话锁定持续时间、会话积压、热键和卡住会话时间；
- 交易失败、重复检测行为和计划交付延迟；
- 命名空间容量、分区健康状况、网络错误和身份验证失败；和
- 消费者并发性、处理延迟、依赖性错误和重试率。

告警应与业务影响挂钩。支付指令的死信数量不断增加比非关键分析订阅的死信数量更加紧迫。按消息类型、期限、积压耗尽时间和下游后果定义严重性。

Runbook 应涵盖生产者中断、消费者中断、依赖项中断、毒消息、架构不兼容、重复发送、锁定过期、会话卡住、命名空间限制、私有网络故障、过期凭证、区域故障转移和受控重播。重播必须是可监控的，并且不得在未经核对的情况下覆盖权威业务日志记录。

## 验证
- [ ] 每个队列、主题和订阅都有所有者、用途、消息契约、受众、保留和生命周期状态。
- [ ] 实体选择被证明是点对点、发布/订阅、计划工作、有序会话工作或事务消息传递。
- [ ] 生产者和消费者暂时解耦，异步工作不需要同步可用性。
- [ ] 定义消息身份、相关性、因果关系、模式版本、生产者、业务密钥、分类和跟踪上下文。
- [ ] 消费者是幂等的，并且有重复、重试、超时和副作用后崩溃行为的证据。
- [ ] 测试死信阈值、告警、检查权限、重播、隔离和协调程序。
- [ ] 重试和回退限制可防止毒消息循环和无限制的下游压力。
- [ ] 会话 ID 足够窄，可以保留所需的顺序，而不会创建不必要的热点。
- [ ] 事务边界已日志记录，并不意味着不支持分布式一次性行为。
- [ ] 预定消息具有取消、时区、延迟传递和最大延迟行为。
- [ ] 验证托管身份或范围 SAS 访问、私有连接、加密和诊断脱敏。
- [ ] 队列寿命、积压、死信、交付计数、锁定、会话、事务、吞吐量和限制指标可用。
- [ ] 生产者和消费者中断测试证明消息按照设计保留、重试、耗尽或死信。
- [ ] 区域恢复、凭证轮换、模式演变和受控重放具有当前的操作手册和证据。
