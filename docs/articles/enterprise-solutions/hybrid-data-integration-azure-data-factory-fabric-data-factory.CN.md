# 混合数据集成 - Azure Data Factory 或 Fabric Data Factory

> **决策简介：** 使用 Data Factory 或 Fabric Data Factory 进行受控数据移动和管道编排。将业务消息传递、同步 API 和应用逻辑保留在专门构建的服务中。

## 目的

此体系结构使用 Azure Data Factory 或 Microsoft Fabric 中的 Data Factory 跨云和私有环境移动、转换、计划和编排数据。典型的工作负载包括批量 ETL 和 ELT、数据库和文件复制、本地 SQL 或 Oracle 摄取、文件共享摄取、数据湖加载、管道调度和依赖项编排以及 Databricks 或其他转换引擎的协调。

集成运行时提供管道控制和数据存储或计算服务之间的执行桥梁。自托管集成运行时可以在私有或本地数据源附近运行，并在这些源和云目标之间安全地移动数据。 [Azure Data Factory 介绍](https://learn.microsoft.com/en-us/azure/data-factory/introduction)

Microsoft 将 Microsoft Fabric 中的 Data Factory 描述为下一代 Azure Data Factory，并建议将 Fabric Data Factory 作为新数据集成项目的起点。现有的 Azure Data Factory 部署不会自动过时：当现有的 ADF 资产仍然适合其工作负载、治理、网络、运营模型和投资时，会保留和发展现有的 ADF 资产。将 Fabric 的采用视为有证据的绿地或迁移决策，而不是计划外的替代任务。 [Microsoft Fabric 中的 Data Factory 是什么](https://learn.microsoft.com/en-us/fabric/data-factory/data-factory-overview)
Data Factory 是数据移动和管道编排边界，而不是事务性企业消息代理、同步 API 集成层或通用应用运行时。使用[企业消息传递 - Azure Service Bus](enterprise-messaging-azure-service-bus.md) 来执行持久业务命令，使用 [事件驱动集成 - Azure Event Grid](event-driven-integration-azure-event-grid.md) 来执行离散状态更改通知，使用 [工作流编排 - Azure Logic Apps](workflow-orchestration-azure-logic-apps.md) 来执行连接器密集型业务流程。

## 范围和设计成果

当工作负载需要执行以下操作时，请使用此模型：

- 在本地、私有云和云数据存储之间复制数据；
- 运行具有显式依赖性和参数化的预定批量 ETL 或 ELT；
- 将数据库、表、文件或变更流复制到数据湖、Lakehouse、仓库或分析存储中；
- 摄取 SQL Server、Oracle、文件共享、SFTP、对象存储、SaaS 或其他支持的数据源；
- 当文件到达或定义的时间表、窗口或依赖项准备就绪时触发摄取；
- 将转换分派到 Databricks、Spark、SQL、Fabric Dataflows、笔记本或其他经批准的计算引擎；
- 执行数据验证、质量检查、隔离、水印和核对；或
- 跨开发、测试、登台、生产和恢复环境协调数据产品生命周期。

目标结果是：

- 每个管道、数据集、链接服务、集成运行时、源、目标、转换、计划和数据契约都有一个所有者和生命周期状态；
- 根据绿地状态、分析平台一致性、网络拓扑、治理和迁移成本，特意选择 Azure Data Factory 或 Fabric Data Factory；
- 私有和本地数据访问使用弹性、受监控和修补的自托管集成运行时或经批准的托管网络替代方案；
- 摄取是增量的并且可在数量或恢复要求合理的情况下重新启动；
- 数据移动、转换、验证、隔离和发布阶段是明确且可监控的；
- 保护源系统和目标系统免受无限并发、重复提取和重试放大的影响；
- 模式、质量规则、数据血缘、分类、保留和访问控制通过管道跟踪数据；和
- 业务工作流程、事务命令、事件通知和应用逻辑保留在适合用途的服务中。

## 背景和决策驱动因素

混合数据集成通常跨越不同的数据库引擎、文件格式、网络、时间表、所有权边界和数据质量期望。管道必须协调移动和转换，而不要求每个源公开公共端点或每个目标了解每个上游系统的详细信息。

该决定的驱动因素是：

- **工作负载形状：** 批量、增量、CDC、基于文件、计划、依赖驱动或转换引擎编排。
- **源和目标覆盖范围：** 本地数据库、私有文件共享、云存储、SaaS 系统、数据湖、Lakehouse 和仓库。
- **新建与资产：** 工作负载是在 Microsoft Fabric 中启动还是必须与已建立的 Azure Data Factory 资产共存。
- **分析对齐：** 需要 Fabric 工作区、Lakehouse、Dataflows Gen2、Fabric 管道、OneLake、实时分析或现有 Azure 数据服务。
- **网络和安全：** 私有端点、托管虚拟网络、ExpressRoute 或 VPN、防火墙、DNS、客户管理的密钥和数据驻留要求。
- **规模和性能：** 数据量、文件计数、并行性、源限制、转换持续时间、SLA 和恢复时间。
- **运营模型：** 工作空间和容量所有权、集成运行时修补、CI/CD、监控、数据血缘、支持和成本管理。
- **迁移和连续性：**现有管道、连接器、触发器、SSIS、链接服务、依赖项、运行历史记录和再培训成本。

### 绿地指导

对于新的数据集成项目，当组织具备经批准的 Fabric 租户、工作区、容量、安全模型、数据治理模型和分析目标时，可以从 Fabric Data Factory 开始。在提交之前确认连接器覆盖范围、混合连接、私有网络、源和目标支持、CI/CD、监控、成本、区域可用性和数据驻留。
Fabric Data Factory 结合了数据移动、Dataflows Gen2、管道、面向 Lakehouse 的工作流程和 Fabric 分析集成。绿地决策 MUST 确定日志系统、目标数据模型、计算引擎、保留策略、访问模型、恢复目标和操作所有者。

### 现有 Azure Data Factory 指南

当现有 ADF 部署的管道、连接器、集成运行时、网络控制、监控、治理和操作模型满足工作负载要求时，它仍然是受支持的架构。不要仅仅为了遵循产品标签或重置积累的平台知识而进行迁移，而不会带来可度量的好处。

当工作负载需要与 OneLake、Fabric Lakehouses、Dataflows Gen2、Fabric Notebook、实时分析、统一治理或新 Data Factory 功能更紧密集成时，评估 Fabric 迁移。当资产具有成熟的 Azure 原生控件、私有连接器、SSIS 要求、私有网络拓扑、契约约束或超过收益的迁移风险时，评估是否继续使用 ADF。

迁移 MUST 被视为托管变更。清单 MUST 包括管道、触发器、链接服务、数据集、集成运行时、凭据、计划、参数、依赖项、自定义活动、SSIS 包、运行手册、SLA、成本和历史证据。在停用 ADF 实施之前，使用代表性卷、私有连接、故障行为和恢复来测试新平台。

## 管道和数据移动模型

### 流水线阶段

使每个流水线阶段明确且可独立监控：
1. **触发和参数解析：**确定时间表、文件到达、依赖完成、水印、环境和处理窗口。
2. **源准备和授权：** 验证源可用性、凭据、模式版本、网络路径和提取范围。
3. **提取或复制：** 通过选定的集成运行时移动有界批次、更改的行、文件集或源分区。
4. **数据落地和完整性：** 使用源元数据、到达时间、校验和或控制总数以及不可变或追加友好的处理写入原始数据。
5. **验证和隔离：** 应用架构、完整性、类型、范围、重复、引用、恶意软件和数据质量检查。
6. **转换：** 调度到映射数据流、Dataflows Gen2、SQL、Databricks、Spark、笔记本或其他批准的引擎。
7. **发布：** 以原子方式或通过版本化发布边界编写策划或提供数据。
8. **协调并通知：** 记录计数、水印、质量结果、数据血缘、新鲜度、输出版本和下游完成情况。

管道不应隐藏单个大型表达式或笔记本调用中的所有逻辑。保持移动、转换、验证和发布契约足够清晰，以便操作员识别失败的阶段并仅恢复所需的工作。

### 批量 ETL 和 ELT

当由于源限制、隐私、兼容性、容量或目标契约而必须在数据到达目标之前转换数据时，请使用 ETL。当目标 Lakehouse、仓库、SQL 引擎或转换平台适合转换原始或暂存数据时，请使用 ELT。

定义原始层、暂存层、策划层和服务层。每个层都应该有一个所有者、模式、保留、访问策略、质量状态和发布规则。如果没有记录在案的校正和保留设计，请勿覆盖原始数据。避免使用流水线运行日志作为加载或转换数据的唯一日志记录。

### 数据库和文件复制

对于数据库复制，根据源能力和恢复要求选择完全加载、增量水印、更改跟踪、CDC、基于日志的复制或其他方法。定义主键、更新和删除处理、后期更改、事务边界、源隔离、快照一致性和协调。

对于文件复制，定义文件命名、完成标记、稳定性检查、校验和、源所有权、加密、架构、重复文件行为、隔离、存档、保留和删除。文件到达触发 MUST NOT 开始处理部分上传的文件。使用源无法提供原子发布操作的清单或控制文件。

复制不是自动同步。文档方向、冲突策略、延迟、删除语义、重新启动行为以及目标是否是可恢复副本、分析副本或权威日志系统。

### 本地 SQL、Oracle 和文件共享摄取
当源是私有的、本地的、位于防火墙后面或者需要自定义驱动程序或本地网络路径时，请使用自托管集成运行时。将运行时安装在靠近数据源的受支持、受监控的主机上或已批准的已连接 Azure 网络中。主机 MUST 控制与 Data Factory 控制平面的出站连接以及所选架构所需的源路径和目标路径。

源连接应使用最低权限的身份、可能的只读访问、有界查询、源端索引和记录在案的提取窗口。当水印或 CDC 机制可用时，不要在每个计划中运行无界表扫描。

对于 Oracle、SQL Server 和文件共享，验证驱动程序版本、编码、排序规则、时区、数字精度、LOB 行为、网络数据包大小、查询超时、文件锁定和源维护行为。在数据契约中记录源架构和兼容性假设。

### 数据湖加载

使用源和摄取元数据加载原始数据或青铜数据。首选不可变或面向追加的文件以及平衡查询性能、文件计数、保留和重播的分区方案。定义目标格式、压缩、模式演变、小文件压缩、加密、生命周期和访问策略。

流水线 MUST 使部分或失败的加载与已发布的数据分开。使用临时路径、清单文件、类似事务的表格式、版本化分区或其他批准的发布方法，这样消费者就不会读取不完整的批次。

当字节到达时，数据湖加载尚未完成。记录行数、文件数、控制总数、源水印、质量结果、处理版本和发布状态。向下游消费者展示新鲜度和完整性。

### 调度和依赖编排

根据工作负载使用计划、滚动窗口、事件、存储或依赖触发器。定义时区、夏令时行为、预期节奏、错过运行策略、重叠策略、窗口延迟、追赶行为和手动重新运行器。

依赖关系 SHOULD 是明确且有界的。管道不应无限期地轮询不相关的系统或使用隐藏的外部标志作为其唯一的完成信号。使用管道参数、元数据表、控制文件、事件触发器或具有所有者和超时的已批准的编排服务。

对于跨域依赖关系，定义信号是否意味着源完成、数据可用性、验证成功或业务批准。Event Grid 可以宣布文件或资源状态更改，但数据管道仍然负责数据准备情况和质量。Logic Apps 可以围绕管道编排连接器密集型业务步骤，但管道负责数据移动和转换。

### Databricks 和转换引擎编排

当管道必须协调依赖项、参数、重试、计划和发布时，使用 Data Factory 或 Fabric 管道调用 Databricks 作业、笔记本、Spark、SQL、Dataflows Gen2、Fabric 笔记本或其他转换引擎。
转换引擎团队负责代码、库、集群或计算、作业逻辑、单元测试、状态、输出契约和运行时兼容性。管道团队负责调用契约、上游准备情况、超时、重试边界、输出验证和下游依赖项。避免重叠的重试策略，其中管道和转换引擎都重试相同的非幂等操作。

通过批准的参数和机密引用传递配置。不要将凭据或大型数据有效负载放置在管道参数中。使用清单或表传递批次标识、源水印、目标版本、架构版本和处理模式。

## 集成运行时架构

### Azure 集成运行时

使用 Azure 集成运行时进行支持的云数据移动和活动调度。它提供托管计算，并且可以根据数据路径进行区域选择或自动解析。验证公共端点、托管虚拟网络、私有端点、数据驻留和出站 IP 要求，而不是假设每个连接器都使用相同的网络路由。

### 托管虚拟网络集成运行时

当平台和连接器支持私有 Azure 数据路径而不操作运行时节点时，请使用托管虚拟网络集成运行时和托管私有端点。确认可以通过所需的私有端点、DNS、网络规则和连接的本地路径访问数据源。如果通过连接的 Azure 网络到达本地环境，请验证 ExpressRoute 或 VPN 路由和防火墙策略。

### 自托管集成运行时

使用自托管集成运行时进行本地数据访问、私有网络、自定义驱动程序或需要在源附近执行的数据源。 Microsoft 将其与 Azure 和 Azure-SSIS 运行时一起视为受支持的集成运行时类型之一。 [选择正确的集成运行时配置](https://learn.microsoft.com/en-us/azure/data-factory/choose-the-right-integration-runtime-configuration)

自承载运行时是一个操作边界，而不是一次性连接器。维护：

- 当管道 SLO 需要运行时连续性时，高可用性集群中至少有两个节点；
- 支持的操作系统、运行时版本、补丁、自动更新和过期监控；
- 并发复制、压缩、加密、自定义驱动程序、内存和临时磁盘的主机大小调整；
- 到 Data Factory 或结构控制平面、Azure 中继或应用的私有链接路径、源、目标、Key Vault 和监视服务的出站网络规则；
- 本地服务身份、注册密钥保护、节点访问和管理分离；
- 源和目标连接限制、并发上限和背压；
- 运行时健康状况、节点计数、CPU、内存、磁盘、队列、作业和连接遥测；和
- 重建、恢复、节点更换、凭证轮换和紧急隔离程序。
自托管运行时不会自动确保私有源的安全。使用源授权、网络分段、防火墙规则、私有 DNS、加密、数据分类和管道级访问控制。

## 数据契约、质量和一致性

每个源到目标的移动 MUST 有一个数据契约，定义源所有者、目标所有者、模式、键、单位、时区、编码、可空性、精度、分类、保留、预期数量、水印、删除行为和质量规则。

质量检查应包括：

- 模式和类型兼容性；
- 必填字段、空值率、范围、精度和单位；
- 重复的钥匙和重复的文件；
- 行、文件、字节和控制总计协调；
- 参考和业务规则验证；
- 新鲜度、完整性和迟到阈值；
- PII、支付、机密和监管数据检测；
- 格式错误的日志、不受支持的编码和损坏的文件；和
- 源到目标计数、水印和删除语义。

将技术成功与数据质量成功分开。当数据不完整、陈旧、重复或无效时，复制活动可能会完成。流水线 MUST 发布下游消费者可以评估的质量和完整性状态。

尽可能使用幂等负载。重新运行相同的批次、水印、文件或源分区不应创建重复的目标数据或损坏已发布的分区。使用合并键、加载 ID、清单、源版本、目标表约束、暂存区域或版本化发布。

Data Factory 管道活动的成功不是跨源、运行时、目标、存储和转换引擎的分布式事务。使用暂存、检查点、类似发件箱的源模式、协调、补偿清理和受控重新运行来实现跨系统一致性。

## 安全和网络架构

将 Microsoft Entra 托管标识或工作负载标识用于 Data Factory、Fabric、存储、Key Vault、Databricks、SQL 和其他受支持的服务。单独的创作、部署、运行时、源、目标和操作身份。范围访问所需的确切工厂、工作区、管道、链接服务、机密、存储容器、数据库架构、表、文件路径和计算作业。

保护 Key Vault 或批准的机密管理服务中的连接字符串、密码、证书、注册密钥、SAS 令牌和驱动程序凭据。不要将机密提交到管道 JSON、笔记本、参数文件、链接服务定义或源代码控制。与所有者轮换凭证、重叠过程、验证测试和回滚路径。

对于敏感或私有集成：

- 在需要时使用私有端点、托管私有端点、私有 DNS、ExpressRoute 或 VPN、防火墙和批准的路由；
- 将自托管运行时主机限制为批准的网络路径和管理访问权限；
- 验证每个连接器是否使用 Azure 运行时、托管虚拟网络运行时、自托管运行时或单独的托管连接路径；
- 使用源端最小权限和只读访问进行摄取，除非明确需要写访问；
- 对传输中和静态的数据进行加密，并在分类需要时应用客户管理的密钥；
- 对流水线日志和错误消息中的有效负载、机密、连接详细信息和受监管字段进行脱敏；
- 根据生命周期和信任边界分离生产、非生产、合作伙伴、受限和恢复工厂或工作区；和
- 审计管道、触发器、链接服务、集成运行时、机密、网络、数据质量、模式和访问更改。

Data Factory 移动和转换数据；它不授权商业行为。源系统和目标系统仍然负责身份验证、授权、租户隔离、事务规则和域完整性。

## 性能、可靠性和成本

围绕源提取限制、目标写入限制、集成运行时节点、复制并行性、文件计数、事件量、分区、压缩、网络带宽、转换计算、并发、计划重叠、重试卷、存储、私有连接和监控来规划容量。

使用适合源端的增量提取、分区读取、批处理、批量加载、压缩、并行复制和适合目标的写入模式。在测量源、运行时、网络、目标和下游查询工作负载之前，不要增加并行度。通过耗尽生产数据库来更快完成的管道并不成功。

重试 MUST 受到限制并仅限于瞬时故障。定义复制、连接器、运行时、笔记本、Databricks 作业和发布阶段的重试边界。避免在没有安全操作密钥的情况下从管道和子引擎重试非幂等转换或目标写入。

对于关键管道，设计应考虑：

- 源不可用和维护窗口；
- 自托管运行时节点丢失或全集群中断；
- 网络、DNS、私有端点、防火墙和凭证故障；
- 部分复制、损坏的文件、模式更改、数据质量故障和隔离；
- 目标限制、存储中断、数据库锁定和转换引擎故障；
- 错过计划、重叠运行、卡住依赖性和延迟数据；
- 区域、工作空间、工厂、容量或控制平面中断；和
- 恢复、重播、协调安全发布。

成本估算 MUST 包括 Azure Data Factory 或 Fabric 容量、管道和活动执行、数据移动、Dataflow Gen2、自托管运行时主机、私有端点、网关、存储、Databricks 或 Spark 计算、监视、网络出口、支持以及迁移或培训。检查空闲运行时间、过多轮询、完全重新加载、重复副本、高频触发器、保留的运行历史记录、超大集群和不必要的数据移动。

## 部署和生命周期

将工厂、Fabric 工作区、管道、数据集、链接服务、触发器、参数、变量、集成运行时、数据流、笔记本、架构、质量规则、告警和网络依赖项作为版本化部署输入进行管理。通过具有适合数据分类和业务影响的批准的环境进行晋级。

每个管道版本 SHOULD 包括：

- 源和目标契约测试；
- 代表性的完整、增量、CDC、文件、模式更改和最新数据测试；
- 私有网络、自托管运行时、凭据、驱动程序、DNS 和防火墙测试；
- 数据质量、隔离、行计数、控制总计、水印和协调测试；
- 重试、超时、取消、部分加载、重复、重新运行和恢复测试；
- Databricks、Spark、SQL、notebook、Dataflow 或外部引擎兼容性测试；
- 计划、依赖性、重叠、手动运行、回填和错过运行的测试；
- 部署、参数、机密、模式、数据血缘、监控和回滚证据；和
- 容量、成本、保留和灾难恢复审查。

对于 ADF 到 Fabric 的迁移，首先要盘点资产并对其进行分类。选择具有私有来源、自托管运行时、增量移动、转换、依赖性、质量检查和故障恢复的代表性试点。在迁移更大的域之前比较数据正确性、性能、成本、监控、数据血缘、访问、部署和支持。保留 ADF 后备和回滚计划，直到 Fabric 实现有生产证据为止。

版本流水线定义及其调用的数据协定和转换接口。架构、分区、水印、连接、运行时或触发器更改可能会改变正在进行的和将来的运行。定义正在进行的运行是继续、取消、迁移还是手动协调。

## 可观测性和操作

数据平台团队负责经过批准的 Azure Data Factory 和 Fabric 模式、工作区、容量、集成运行时、网络集成、身份、连接器、CI/CD、监控和共享 Runbook。源团队负责源可用性、契约、提取语义和数据质量。数据产品团队负责目标模型、转换、消费者 SLO 和发布。安全和治理团队定义访问、隐私、数据血缘、保留、审计和例外要求。

每个生产流水线都应该有一个操作记录，其中包含所有者、目的、源和目标、数据契约、分类、集成运行时、时间表、依赖关系图、预期数量、水印、转换引擎、SLO、成本中心、支持路径、恢复点、重播过程以及退役或审核日期。

至少监控：

- 管道和活动成功、失败、持续时间、取消、重试、超时和并发；
- 触发器触发、延迟、错过计划、重叠运行、依赖项时长和流水线阻塞；
- 源和目标连接健康状况、查询持续时间、行计数、文件计数、字节计数、吞吐量和限制；
- 自托管运行时节点健康状况、版本、CPU、内存、磁盘、并发、队列、注册和连接；
- 数据新鲜度、完整性、质量评分、隔离计数、重复计数、架构漂移和协调状态；
- 水印、CDC、检查点、增量边界、删除处理、迟到和回填状态；
- Dataflow、Databricks、Spark、SQL、notebook、Fabric 容量、集群、作业和状态存储运行状况；
- 数据湖、lakehouse、仓库、存储、私有端点、DNS、防火墙和 Key Vault 运行状况；
- 管道、连接器、链接服务、触发器、集成运行时、工作空间、容量、身份、机密和网络更改；和
- 成本、数据移动、活动量、存储、运行时利用率、容量利用率和空闲资源趋势。

Runbook 应涵盖源中断、目标中断、自托管运行时节点或集群故障、驱动程序或版本到期、私有网络故障、凭证到期、架构漂移、数据质量故障、部分复制、损坏的文件、卡住的依赖项、重叠计划、Databricks 或 Spark 故障、Fabric 容量耗尽、ADF 到 Fabric 回滚、受控重播、回填和管道报废。

## 验证

- [ ] 工作负载是数据移动、转换、调度或依赖项编排，而不是事务性业务工作流或离散事件通知。
- [ ] Azure Data Factory 或 Fabric Data Factory 是从绿地状态、分析一致性、连接器、网络、治理、容量、成本、迁移和运营模型要求中选择的。
- [ ] 现有 ADF 工作负载具有由清单、风险、成本和能力证据支持的明确保留、现代化或迁移决策。
- [ ] 每个源、目标、管道、数据集、链接服务、触发器、转换、集成运行时、契约和所有者均已日志记录。
- [ ] 自托管集成运行时拓扑、节点高可用性、修补、版本、驱动程序、凭据、出站路径、源访问、目标访问和监控均经过验证。
- [ ] 本地 SQL、Oracle、文件共享、SFTP、私有数据库和云源访问使用最小权限、有界提取、稳定的网络路径和经过测试的连接。
- [ ] 定义 ETL 或 ELT 层、原始或青铜登陆、策划或服务发布、模式、数据血缘、保留和访问模型。
- [ ] 在应用的情况下记录了完整、增量、CDC、水印、文件清单、删除、最新数据、重复、重新启动和协调语义。
- [ ] 测试分区、并行性、批量大小、并发性、源限制、目标限制、转换容量以及峰值或恢复负载。
- [ ] 测试管道重试、超时、取消、重叠、依赖性、部分失败、隔离、重新运行、回填和发布行为。
- [ ] Databricks、Spark、SQL、Dataflow、notebook、Fabric 或其他转换引擎契约和重试边界是明确的。
- [ ] 验证身份、机密、证书、私有端点、DNS、防火墙、加密、客户管理的密钥、数据分类和日志脱敏。
- [ ] 提供数据质量、模式兼容性、控制总数、行数、新鲜度、完整性、漂移、隔离和消费者发布证据。
- [ ] ADF 到 Fabric 的迁移具有代表性试点、性能和成本比较、回滚计划以及应用的生产支持准备情况。
- [ ] 仪表板、告警、数据血缘、支持联系人、依赖 SLO、运行时运行状况、成本限制、恢复程序和退役证据在生产前准备就绪。
