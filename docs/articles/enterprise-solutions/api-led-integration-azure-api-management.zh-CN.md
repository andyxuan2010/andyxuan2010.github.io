# API 主导的集成 — Azure API Management

> **决策简述：** 使用 APIM 作为共享 API 外观和策略边界。将业务逻辑保留在后端，并在 API 的风险或拓扑需要时使用私有连接。

## 目的

此体系结构使用 Azure API Management (APIM) 作为员工、合作伙伴、公共客户和内部应用使用的 API 的受控 Front Door。它提供一致的 API 契约和策略边界，同时允许实施保留在 Azure 计算、本地系统、Kubernetes 或其他云上。

该设计标准化了身份验证和 JWT 验证、速率限制、配额、缓存、请求和响应转换、API 发现、生命周期治理和遥测。它还提供了围绕遗留系统的迁移接缝，因此消费者可以采用稳定的 API，而无需等待每个后端都进行平台重构。

APIM 是一个混合多云 API Management 平台。它的网关是一个运行时代理和策略执行点；其管理平面和开发人员门户提供配置、发布、发现和消费者入驻服务。 APIM MUST NOT 成为应用运行时或隐藏的集成单体。大量的业务逻辑、长时间运行的编排、数据转换工作流和域授权属于适当的后端或集成服务。

## 范围和设计成果

当组织需要执行以下操作时，请使用此模型：

- 向员工或工作负载团队发布内部 API；
- 通过受控的入驻、产品、订阅和配额公开合作伙伴 API；
- 公开批准的公共 API，无需将消费者耦合到后端拓扑；
- 在 Azure 和非 Azure 后端上提供一致的界面；
- 在 API 边界验证 OAuth 2.0 或 OpenID Connect 访问令牌；
- 应用横切策略，例如节流、缓存、标头标准化和协议转换；
- 提供中央 API 目录、文档和所有权模型；或
- 通过稳定的外观逐步实现遗留系统的现代化。

目标结果是：

- 每个已发布的 API 都有所有者、生命周期状态、契约、受众和支持路径；
- 消费者使用受管理的 API 主机名而不是直接后端地址；
- 一致地应用身份验证、授权输入、配额和可观测性；
- 后端位置和实现可以更改，而无需消费者进行不必要的更改；
- 策略变更通过环境进行版本控制、审查、测试和晋级；和
- 网关仍然是可预测的、快速的，并且仅限于跨领域的关注点。

## 背景和决策驱动因素

点对点集成创建了越来越多的特定于客户端的凭据、网络路径、重试行为、协议假设和未记录的依赖项。直接发布后端端点还会公开实现细节，并使跨团队应用一致的控制变得困难。

该架构由以下约束和质量属性驱动：

- **受众分离：** 内部、合作伙伴和公共消费者有不同的信任、支持、入驻和配额要求。
- **后端多样性：** 单个 API 资产可能跨越 App Service、Functions、AKS、虚拟机、SaaS 系统、数据中心服务和其他云。
- **身份强制执行：** 在转发请求之前，网关必须拒绝无效或范围不正确的令牌。后端授权对于资源级别和业务决策仍然是必要的。
- **受控变更：** API 契约、版本、策略和产品必须在不悄然破坏消费者的情况下进行晋级。
- **私有连接：** 私有 API 应使用经批准的虚拟网络、私有链接、ExpressRoute、VPN 或等效路径，而不是公开暴露。
- **遗留现代化：**外观应允许分阶段替换遗留协议或数据模型，而不在网关策略中嵌入不可维护的域工作流。
- **操作证据：** 请求结果、延迟、后端故障、策略决策、容量和消费者使用情况必须支持事件响应和服务级别目标。
- **成本和规模：** 层、容量、区域布局、自托管网关占用空间、缓存行为和流量形状必须根据测量的需求进行选择。

## 考虑的选项

### 直接客户端到后端的暴露

此选项对于单个应用来说很简单，但会创建重复的身份验证、限制、转换、日志记录和重试行为。它公开了后端拓扑，并使合作伙伴或公共加入不一致。仅对于严格限制的私有服务到服务调用是可接受的，其中 API 网关不属于所需控制边界的一部分。

### 应用负责的网关或反向代理

应用团队可以在其服务附近操作网关或反向代理。这可能适合专门的协议、特定于应用的聚合层或非常小的部署。当多个团队、消费者、产品或信任区域需要通用控制时，它不应取代共享 API 治理模型。

### 服务网格入口

服务网格可以在集群内提供工作负载到工作负载的身份、流量策略和遥测。它不能替代企业 API 产品目录、合作伙伴入驻、公共 API 管理或跨环境 API 外观。在 Kubernetes 工作负载需要时，将其用作补充的东西向控制。
### 集成工作流程或自定义适配器作为 Front Door

Logic Apps、函数或自定义适配器可能是编排、异步工作流程或大量数据转换的正确运行时。将该逻辑直接放置在 APIM 策略中会增加延迟、测试复杂性、策略传播半径和操作模糊性。当通过受管理的 API 使用工作流时，请在运行时之前使用 APIM。

### 选择方向：Azure API Management

使用 APIM 作为共享 API 外观和策略执行层。将其托管网关用于 Azure 托管或集中访问的 API。当数据平面应在数据中心、Kubernetes 集群或其他云中的 API 附近运行，同时组织保留基于 Azure 的管理和治理时，请使用自托管网关。将 WAF、边缘路由、私有连接和后端运行时放置在适当的层中。

托管网关是可通过所选 Azure 网络设计访问的 API 的默认数据平面。自托管网关是部署在后端附近的基于 Linux 的容器化数据平面；它通常在 Kubernetes 上运行。这两个网关仍然受集中管理的 API 定义、产品、策略和发布控制的约束。网络布局、DNS、防火墙规则和私有连接 MUST 可防止消费者绕过批准的网关路径。

可选的边缘边界用于面向互联网的保护和路由。带有 WAF 的 Application Gateway 或 Front Door 可以在 APIM 之前检查和路由公共流量；然后，APIM 应用特定于 API 的身份验证、授权输入、配额、转换、缓存和后端路由。请勿将 APIM 视为 WAF、全局边缘、通用负载均衡器或应用运行时的替代品。

## API 受众和产品模型

通过产品、群组、订阅和显式访问策略来代表消费者意图。共享 APIM 实例 MAY 为多个受众提供服务，但 API 平台必须保留明确的所有权和信任边界。

|观众|典型的进入路径|所需的控制|出版模型|
|---|---|---|---|
|内部|私有 DNS 和托管网关或批准的内部端点 | Entra ID、工作负载身份、最低权限授权、消费者配额、私有连接 |具有基于组的可见性的内部产品 |
|合作伙伴| 公共边缘或私有合作伙伴连接后接入 APIM |联邦身份或客户凭证、合作伙伴特定产品、配额、契约、支持联系人、威胁监控 |受控的加入和明确的订阅批准|
|公共| 公共边缘后接入 APIM | JWT 或批准的凭证验证、滥用控制、速率限制、版本控制、威胁防护、公共文档 |具有已发布条款和支持路径的公共产品 |
不要使用订阅密钥作为敏感 API 的唯一授权机制。订阅密钥标识应用或产品订阅并支持使用管理；它们不会取代令牌验证、后端授权或网络控制。对于处理敏感数据或特权操作的 API，需要经过验证的令牌并强制执行适合操作的范围、角色、受众、租户和资源授权。

## API 契约和生命周期

从经过审核的 OpenAPI、WSDL、GraphQL、gRPC 或其他应用的支持契约发布 API。契约应定义：

- 资源和操作语义；
- 认证和授权要求；
- 错误形状、相关标识符和重试指导；
- 幂等性和并发行为；
- 分页、过滤和响应大小期望；
- 速率限制标头和配额行为；
- 数据分类和敏感领域；和
- 所有者、支持路径、弃用策略和版本控制策略。

使用产品为消费者群体打包 API，并使用开发人员门户来发布文档、接入、订阅和交互式发现。当资产包含 APIM 外部的 API 或发现必须跨越生命周期阶段和部署位置时，使用 API Center 作为组织范围的清单。门户和目录是互补的：门户解释了经过批准的消费者如何使用 API，而清单则确定存在的内容、所有者以及部署位置。

故意版本 API。更喜欢版本内追加的、向后兼容的更改。当契约或语义破坏现有消费者时引入新版本，发布迁移期，度量剩余使用情况，并仅在所有者批准的证据支持退役后删除旧版本。网关重写或转换可以弥补临时的兼容性差距，但它 MUST NOT 隐藏无限期不受支持的契约。

## 认证与授权

网关应在请求到达后端之前执行早期请求身份验证和粗略授权：

- 根据已批准的身份提供商配置验证 JWT 签名、颁发者、受众、到期日和所需声明。
- 需要适合 API 产品和操作的范围或角色。
- 单独的员工、合作伙伴、客户和工作负载身份颁发者，除非记录在案的联合模型提供同等保证。
- 拒绝具有一致错误行为的丢失、格式错误、过期、错误颁发或范围错误的令牌。
- 在合作伙伴保证、设备身份或私有连接需要时，使用相互 TLS 或其他经批准的客户端身份验证机制。
- 通过批准的机密管理模式解决机密、证书和签名配置问题；不要将长期凭据放置在源代码管理或不受保护的策略文本中。
- 仅转发后端设计信任的声明和标头，并防止消费者欺骗网关添加的身份标头。
网关验证是必要的，但还不够。后端 MUST 使用其信任的主体、租户、服务身份或声明来授权所请求的资源和操作。有效的令牌证明身份或委托授权；它本身并不证明调用者可以读取特定的客户日志或执行业务操作。

## 策略和转型边界

使用 APIM 策略实现确定性、有界、横切行为：

- 路由选择和后端选择；
- JWT、订阅、证书或基于 IP 的检查；
- 速率限制、并发限制和配额；
- 响应缓存以实现安全且范围正确的操作；
- 标头标准化、相关 ID 和协议中介；
- XML/JSON 或其他有界请求和响应转换；
- 内容类型、大小、方法和所需参数的验证；和
- 在操作和故障语义允许的情况下受控重试或断路行为。

将这些问题排除在网关策略层之外：

- 多步骤域工作流程；
- 长时间运行或异步编排；
- 跨系统的复杂连接；
- 需要域名所有权的权威业务规则；
- 大有效负载处理或文档转换；
- 跨独立系统的交易协调；和
- 做出业务决策所需的持久状态。

使用 Logic Apps、函数、容器化服务、应用运行时、消息传递工作流或专门构建的集成服务来履行这些职责。 APIM 可以前置该运行时并将其公开为受管理的 API，但它不应该成为运行时本身。

## 后端连接和遗留现代化

后端契约应保持独立于实施的物理位置。优先选择私有 API 的私有连接并记录完整路径，包括 DNS、路由、防火墙、TLS 和源身份。

对于 Azure 后端，请为所选服务使用批准的虚拟网络、私有端点、服务端点或公共入口模式。对于本地后端，请使用 ExpressRoute、站点到站点 VPN 或批准的私有集成路径。对于 Kubernetes 和其他云，当位置、延迟、出口控制或监管要求不适合集中式网关时，请将自托管网关部署在靠近 API 的位置。

自托管网关并不能消除对弹性本地设计的需求。提供：

- 跨节点或故障域的冗余网关副本；
- 对 Azure 管理和配置端点的受控访问；
- 遵循平台标准的本地证书、机密和身份处理；
- 限制网关到后端流量的网络策略和防火墙规则；
- 当网关无法到达管理平面时记录在案的行为；和
- 经过测试的升级、回滚和紧急支持程序。
对于遗留现代化，从围绕稳定业务能力的狭窄外观开始。在边界处转换协议、身份验证、标头或有效负载形状时保留所需的遗留语义。逐步将域行为移至替换运行时，比较新旧行为，并仅在消费者和操作证据支持更改后才停用旧路由。不要发布仅公开每个旧表或内部端点而没有面向消费者的契约的瘦外观。

## 安全性、弹性和成本

### 安全

- 在威胁模型需要时，将公共入口置于经批准的 WAF、DDoS 和边缘控制后面。
- 在可行的情况下，对内部和敏感 API 使用私有 APIM 和后端路径。
- 将最低权限 RBAC 应用于管理平面、工作区、API 定义、产品、策略和命名值。
- 使用 Key Vault 或同等认可的服务保护证书、客户端机密、签名材料和后端凭据。
- 设置请求大小、响应大小、超时和内容类型限制，以减少滥用和资源耗尽。
- 对日志和跟踪中的令牌、机密、敏感标头和受监管的有效负载字段进行脱敏。
- 监控策略变化、订阅创建、密钥轮换、后端变化和异常消费者行为。

### 弹性和性能

- 使用测量的请求率、负载大小、并发性、策略成本、缓存命中率和后端延迟来选择生产层和容量模型。
- 当业务服务级别目标需要区域弹性时，使用多区域 APIM 或经批准的边缘故障转移模式。
- 定义故障是否应该失败打开、失败关闭、返回缓存的响应或路由到回退后端；不要隐含这一点。
- 绑定重试并避免跨消费者、APIM、服务网格和后端客户端的重试放大。
- 仅缓存安全、密钥正确、经过适当授权且在定义的新鲜期内有效的响应。
- 测试托管和自托管网关升级、配置传播、节点丢失、身份提供商故障、后端故障和管理平面不可用。

### 成本

主要成本驱动因素包括 APIM 层和容量、区域数量、自托管网关基础设施、公共边缘和 WAF 使用、私有连接、遥测摄取、缓存服务和后端执行。不要仅从请求计数中选择层。包括 API 数量、策略复杂性、有效负载大小、并发性、可用性目标、网络拓扑和操作支持模型。检查空闲或重复的 API 实例、非托管自托管网关集群、过多的诊断保留和低价值的缓存条目。

## 操作注意事项
API 平台团队负责 APIM 服务、层、网络集成、网关生命周期、共享策略基线、门户配置、目录集成和平台遥测。 API 产品团队负责自己的契约、后端行为、操作级授权、消费者文档、SLO 和弃用计划。安全和治理团队定义身份、数据保护、日志记录和异常要求。

每个 API 都应该有一个操作记录，其中包含所有者、产品、版本、后端、数据分类、受众、依赖项列表、支持路径、SLO、配额、升级路径以及停用日期或审核日期。尽可能以代码管理 API 定义，并以策略即代码方式管理策略定义，在 CI 中对其进行验证，并通过具有适合风险的批准的环境来晋级它们。

至少监控：

- 请求量、状态码、延迟、后端延迟和网关延迟；
- 身份验证失败、授权失败、配额响应和策略错误；
- 缓存命中率、响应大小、超时、重试和断路器行为；
- 后端健康状况、依赖饱和度、连接失败和 DNS/TLS 错误；
- 按 API 版本、租户和地理位置（如果适用）划分的消费者和产品使用情况；
- 网关 CPU、内存、副本健康状况、配置同步和证书到期；和
- 管理平面变更、订阅变更、策略变更和异常访问。

事件操作手册应将 APIM 网关故障与身份提供商故障、边缘/WAF 阻止、网络路径故障、后端故障、策略回归和消费者契约违规区分开来。采集跟踪请求所需的关联 ID 和网关策略上下文，而不保留不必要的敏感负载数据。

## 验证

- [ ] 每个 API 都有一个负责任的所有者、受众、产品、契约、版本、支持路径和生命周期状态。
- [ ] 内部、合作伙伴和公共访问路径明确分开并经过测试。
- [ ] JWT 发布者、签名、受众、到期日、范围、角色和租户声明根据 API 契约进行验证。
- [ ] 后端授权的实施独立于网关令牌验证。
- [ ] 速率限制、配额、请求限制、缓存规则和转换具有基于证据的值和测试。
- [ ] 消费者无法绕过 APIM 来访问受保护的后端。
- [ ] 针对每个后端位置验证私有连接、DNS、路由、防火墙、TLS 和源身份。
- [ ] 自托管网关副本、管理平面连接、配置同步、升级和回滚经过测试。
- [ ] 公共 API 使用经批准的边缘、WAF、DDoS 和威胁监控控制。
- [ ] API 定义和策略经过版本控制、审核、通过环境进行提升并且可恢复。
- [ ] 门户文档和组织范围的 API 清单可识别 API 所有者和部署位置。
- [ ] 网关策略不包含实质性业务逻辑、长时间运行的工作流或隐藏的持久状态。
- [ ] 针对身份、网关、网络、后端、缓存和管理平面中断测试故障行为。
- [ ] 仪表板、告警、操作手册、支持联系人和弃用证据在生产发布之前准备就绪。
