# Ansible 自动化工程标准

## 目的

该标准定义了 Ansible Playbook、角色、集合、清单、执行环境和控制器对象的最低工程、安全、测试、交付和操作控制。它应用于配置系统、协调应用更改、调用云 API、执行合规性修复或执行操作运行手册的自动化。

目标是使自动化能够安全地重复使用并且易于证明。 Ansible 代码必须被视为生产软件：它需要清晰的界面、版本控制、同行评审、自动验证、受控身份、有限的目标范围、可监控的结果和恢复路径。

该标准补充了[基础设施即代码工程标准](infrastructure-as-code-engineering-standard.md)。该标准管理基础设施定义和状态管理控制。本文档管理 Ansible 的行为和执行。如果两个工具都参与同一个生命周期，则架构决策必须确定哪个工具对于每个资源或配置域具有权威性。

## 规范语言

关键字 **MUST**、**MUST NOT**、**REQUIRED**、**SHOULD**、**SHOULD NOT** 和 **MAY** 是规范性的：

- **MUST / MUST NOT**：范围内自动化的强制要求。
- **SHOULD / SHOULD NOT**：预期，除非基于风险的例外情况得到批准。
- **MAY**：可选，根据工作负载需求选择。

如果目标平台或 Ansible 发布版无法直接实现需求，则实现 MUST 提供等效控制并在架构决策记录（ADR）中记录等效性。

## 工程原则

1. **在命令之前使用模块。** 优先使用幂等的、平台感知的模块，而不是 `shell`、`command` 或临时脚本。
2. **明确期望的状态和操作意图。** 角色或 Playbook 必须解释它管理什么、不管理什么以及成功意味着什么。
3. **保持接口狭窄。** 变量、标签、清单、凭证和控制器输入是公共接口，必须进行日志记录和验证。
4. **突变前失败。** 预检查必须在更改目标之前检测到不支持的平台、缺少依赖项、不安全的范围、维护冲突以及容量不足。
5. **限制爆炸半径。** 使用显式清单、平台控制的 `--limit` 限制、串行波、故障阈值和批准边界。
6. **固定执行内容。** 将集合、执行环境、操作系统依赖项和外部内容固定到支持的版本。
7. **不要隐藏机密。** 机密值必须来自批准的提供商，并且绝不能存储在 Git、清单、日志、制品或任务输出中。
8. **测试行为，而不仅仅是语法。**测试必须证明幂等性、安全默认值、故障处理和有意义的后置条件。
9. **证据是交付的一部分。** 每个生产运行都必须可归因、可重复，并与其请求或变更相关。

## 创作和代码设计控制

### Playbook 和角色

Playbook 应该协调角色并公开业务或运营工作流程。角色应该实现一种与一个所有者一致的能力和一个可管理的生命周期。角色 MUST NOT 默默地修改不相关的服务、创建广泛的云资源或更改系统安全设置，而无需声明该行为。

使用任务文件来分隔预检、安装、配置、迁移和验证等阶段。使用处理程序来重新启动服务以及在相关更改后应发生一次的其他通知。避免角色即使在没有更改配置的情况下也总是重新启动服务。

每个角色自述文件都应记录：

- 目的、支持的平台、非目标和所有者；
- 所需的 Ansible 和集合版本；
- 变量、类型、默认值、允许值和敏感性；
- 管理的文件、模板、服务、端口、包、用户和权限；
- 所需的权限和网络访问权限；
- 标签和支持的执行模式；
- 幂等性和检查模式限制；
- 升级、回滚和迁移行为；
- 开发和类似生产使用的示例；和
- 测试、已知限制和支持流程。

### 完全限定名称和模块选择

任务 MUST 使用完全限定的集合名称，例如 `ansible.builtin.package`、`ansible.builtin.service`、`ansible.builtin.template` 和 `ansible.builtin.assert`。这使得依赖项所有权可见并防止行为发生更改，因为集合引入了同名模块。
使用代表目标系统状态的模块。安装包的任务应该使用 package 模块；管理服务的任务应该使用 service 或 systemd 模块；管理文件的任务应该使用文件、副本或模板。仅当不存在合适的模块或 API 时才允许使用 `command` 和 `shell`，并且任务必须定义 `creates`、`removes`、显式更改条件或其他可靠的收敛检查（如果适用）。

不要使用 shell 流水线代替数据处理、在命令字符串中嵌入机密或使用输出是成功的唯一证据的命令。如果需要自定义模块，请将其视为具有自己的代码审查、测试、打包、依赖项扫描和支持所有者的软件。

### 幂等性和收敛性

当将相同的所需输入应用于已经兼容的目标时，自动化运行不会产生意外的更改，因此自动化运行是幂等的。幂等性必须覆盖整个工作流程，而不仅仅是单个任务。

通过以下方式实现收敛：

- 比较突变前的期望状态和观测到的状态；
- 使用稳定的模板和确定性排序；
- 仅当托管输入发生更改时才通知处理程序；
- 避免使用时间戳、随机值或生成的标识符，除非它们有意保持稳定；
- 使 API 重试安全且有界；
- 通过有界轮询处理最终一致性；和
- 记录无法逆转或重复的外部副作用。

某些操作（例如密码轮换、数据库迁移、软件包升级和证书替换）具有故意的一次性效果。他们必须使用显式状态标记、版本、迁移 ID 或其他防护，并且必须记录部分完成后重试的行为方式。

### 变量和输入验证

变量的命名、描述和验证必须一致。优先选择角色默认值以实现安全的可选行为，并要求没有安全通用默认值的值。当具有记录在案的默认值的布尔值更清晰时，请勿使用未定义的变量作为隐式功能开关。

验证应涵盖：

- 类型和形状；
- 允许的枚举值；
- 最小值和最大值；
- 路径和主机名格式；
- 云范围和目标所有权；
- 相互排斥和所需的组合；
- 维护窗口和并发限制；和
- 该值是否敏感或更改权限。

当输入位于角色契约之外时，以下模式在配置更改之前失败：
```yaml
---
- name: Validate baseline inputs
  ansible.builtin.assert:
    that:
      - baseline_ntp_servers is sequence
      - baseline_ntp_servers | length > 0
      - baseline_ssh_port is number
      - baseline_ssh_port >= 1
      - baseline_ssh_port <= 65535
      - baseline_allowed_admin_groups is sequence
    fail_msg: "The baseline input does not satisfy the documented contract."
```
来自控制器调查或 Webhook 额外变量 MUST 映射到键入的输入对象中，而不是直接传递到命令、路径、清单名称或凭证选择器中。

### 清单标准

清单必须区分环境、所有权、服务、平台、区域和生命周期状态。使用稳定的组名称，并避免将可变事实编码到可用清单变量或插件属性的主机名中。

清单文件应仅包含连接元数据和非敏感配置。密码、私钥、不记名令牌、云访问密钥和证书私有材料属于经过批准的机密提供商。清单插件必须记录缓存、刷新、身份验证和错误行为。

建议为每个托管目标或服务组使用以下清单属性：
```yaml
all:
  children:
    service_orders:
      vars:
        service_owner: platform-orders
        service_criticality: high
        maintenance_window: "Sun 02:00-04:00 America/New_York"
        target_environment: production
      hosts:
        orders-01:
          ansible_host: 10.20.4.21
          target_region: eastus
          target_lifecycle: active
```
当所有权、环境、网络可达性或生命周期发生变化时，必须审查清单数据。退役的目标不得仍然有资格从事广泛的生产工作，因为日志记录从未被删除。

## 安全和身份控制

### 凭证处理

凭证 MUST 可通过控制器的凭证集成、Secret Manager 查找或等效的批准代理来检索。不要将机密值放入：

- `group_vars`、`host_vars`、`defaults`、`vars` 或清单文件；
- Git 历史记录、问题评论、拉取请求或示例文件；
- 命令行参数、shell 历史记录或未加密的环境文件；
- 作业制品、事实缓存、回调输出或调试消息；或
- 可以在受保护的测试系统之外发布的测试装置。

仅在可能暴露机密的最小任务块上使用 `no_log: true`。在启用之前，请确保任务具有安全的失败消息和外部关联 ID，以便操作人员可以诊断结果。

### 最小特权和职责分离

目标连接身份应受到主机组、操作系统功能、命令或服务范围以及时间的限制（如果可能）。云身份应受账户、订阅、项目、隔间、资源组、标签条件和 API 操作的限制。

将只读发现、评估、配置、修复和破坏性操作分离到不同的角色或作业模板中。只读清单刷新不应需要与补丁或防火墙更改工作流程相同的凭据。

生产执行必须受到控制器 RBAC 的保护，对于高风险作业，必须受到批准节点或等效变更门的保护。可以允许用户请求作业，但不被允许批准或执行它。

### 供应链安全

集合、角色、执行镜像、Python 包、系统包和自定义插件都是依赖项。固定版本、验证源和受支持的校验和、扫描漏洞和机密，并保留每个版本使用的依赖项清单。

请勿在生产作业期间下载未经审核的内容。生产执行环境应构建在可信流水线中，并通过摘要进行扫描、批准和晋级。如果紧急情况需要临时内容，则紧急日志记录必须标识来源、哈希、审阅者、过期和清理操作。

## 验证

### 验证流水线

最小的 CI 流水线是：
```mermaid
flowchart LR
    A[Pull request] --> B[YAML and syntax validation]
    B --> C[ansible-lint and style checks]
    C --> D[Dependency and secret scan]
    D --> E[Unit and Molecule tests]
    E --> F[Policy and security checks]
    F --> G[Ephemeral integration test]
    G --> H[Build signed or attested execution environment]
    H --> I[Publish immutable release]
```
对于低风险的仅文档更改，流水线可能会省略临时集成测试，但原因应该在变更记录中可见。对身份、网络、修补、备份、加密、软件包仓库或组织级云配置的高风险更改需要集成或等效的受控测试。

### 测试级别

|测试级别|目的|示例 |
|---|---|---|
|解析和语法 |检测格式错误的 YAML 和不受支持的 playbook 语法 | `ansible-playbook --syntax-check`，YAML 解析器 |
|风格和静态分析|检测不安全模式和可维护性缺陷 | `ansible-lint`、yamllint、自定义规则 |
|单元测试或模拟测试 |验证任务分支和变量契约 |分子聚合、模拟模块、角色测试 |
|集成测试|验证真实目标行为 |临时虚拟机、容器、网络设备沙箱、云测试账户 |
|幂等性测试 |验证第二次运行收敛，没有意外的更改 |两次连续收敛并进行变化比较 |
|安全测试|验证权限、机密、传输和安全默认值 |策略检查、机密扫描、访问测试 |
|部署后验证 |验证业务或服务的健康状况 |端点、进程、集群、API 或综合事务检查 |

测试必须包括负面案例。如果角色仅证明有效输入更改了干净的目标，则该角色没有经过充分测试。测试不受支持的操作系统、丢失的软件包、不可用的机密服务、拒绝 API 调用、部分波次、无效的调查值以及在风险允许的情况下中断执行。

### 检查模式和 diff 模式

在模块和目标允许的情况下，角色 SHOULD 支持 `--check` 和 `--diff`。必须记录限制。成功的检查模式运行不会取代真正的测试，因为外部 API、处理程序、权限和最终一致性在突变期间可能表现不同。

不要通过 diff 输出暴露敏感的渲染内容。包含机密或私钥的模板必须禁用相关任务的 diff 并保留安全验证信号。

## 交付和执行控制

### 发布及晋级

当可复用集合和角色具有已发布的接口时，使用语义版本控制。对变量、默认值、支持的平台、权限、托管文件或副作用的重大更改需要主要版本或明确批准的迁移路径。

生产应该使用不可变的发布或提交以及不可变的执行环境摘要。从测试到登台和生产晋级相同的制品；不要使用环境之间的浮动依赖关系来重建它。

每个版本应包括：

- 源码修订和发布版本；
- 依赖关系和执行环境清单；
- 兼容性矩阵；
- 变更摘要和迁移说明；
- 测试和扫描证据；
- 所有者和支持联系人；和
- 已知的回滚或前向恢复限制。

### 作业模板和工作流程设计
生产控制器对象应定义固定项目、Playbook、清单、执行环境、凭证集和允许的输入模式。作业模板不应允许任意凭证选择、任意清单选择、不受限制的额外变量或任意 Playbook 路径。

高风险工作流程应具有单独的节点：

- 目标和版本发现；
- 备份、快照或变更前证据；
- 批准或变更窗口验证；
- 金丝雀执行；
- 健康验证；
- 扩大执行范围；和
- 回滚、前向恢复、通知和关闭。

计划必须包括所有者、时区、预期持续时间、并发性、错过运行行为和禁用过程。事件驱动的触发器必须经过身份验证，并且不得直接执行无限制的用户输入。

### 并发和爆炸半径

每个多目标工作都必须定义一个安全的变更波次。使用 `serial`、`throttle`、控制器分叉、作业并发、集群仲裁规则和故障阈值。广泛的 `all` 目标必须是有意选择的，而不是省略主机模式的结果。

工作设计必须回答：

- 一次改变的目标的最大数量是多少；
- 哪个目标是金丝雀以及如何选择它；
- 失败的目标如何影响下一波；
- 哪些服务健康状况标志着门进程；
- 工作流程是否可以安全地恢复；和
- 人类如何快速停止工作。

### 生产及应急执行

临时命令可以在开发中和批准的事件期间使用，但生产紧急执行仍然必须使用受控身份、目标限制、日志记录和变更记录。事件发生后，必须将更改协调到仓库中或显式还原。

紧急程序不得成为永久的旁路。每项紧急作业都应有有效期、受限凭证、指定操作员、原因、目标范围、结果和使用后审查。

## 操作控制

### 可观测性和证据

生产工作证据必须包括：

- 请求、事件或更改标识符；
- 发起者、批准者和执行者服务身份；
- 仓库、分支或发布、提交和执行环境摘要；
- 清单来源、环境、目标限制和目标数量；
- 开始和结束时间戳、持续时间、任务结果摘要和失败详细信息；
- 在安全可用的情况下更改资源或配置路径；
- 变更后验证结果；
- 调用时回滚或前向恢复结果；和
- 日志、仪表板、票证和后续工作的链接。

不要将绿色控制器状态视为服务运行状况的证明。工作流必须发布有意义的验证结果，并且操作必须能够区分无法到达的目标、跳过的目标、未更改的目标、已更改的目标和失败的目标。

### 故障处理和恢复
任务失败时必须带有可操作的消息，并且应该在不暴露机密的情况下识别目标、预期状态、观测到的状态以及建议的下一步操作。避免 `ignore_errors: true` 进行重大更改。如果故障是故意非阻塞的，请使用注册的结果、显式条件、警告和证据路径。

在进行高风险更改之前，定义恢复是否意味着恢复备份、应用以前的配置、完成正向迁移或禁用功能。如果更改的操作是不可逆的，则角色不得声明回滚。对于数据库迁移、包升级和证书轮换，记录单向边界和恢复替代方案。

### 漂移与合规性

仅当所需状态、事实来源和所有权明确时，才应使用 Ansible 进行计划评估和修复。修复作业不得仅仅因为角色默认值较旧而覆盖有意的异常或较新批准的更改。

漂移处理必须区分：

- 应恢复未经授权的漂移；
- 经批准的以清单或策略为代表的变更；
- 已经超越该角色并需要采用的目标状态；和
- 来源或清单故障导致观测到的结果不可信。

报告应包括首次检测、所有者、严重性、受影响的目标、修复工作、异常参考和年龄。

### 性能和规模

有选择地使用事实。在不需要时禁用或限制事实收集，仅使用记录在案的敏感性和新鲜度策略缓存事实，并在可以安全地重用控制器端查询时避免在每个主机循环内重复 API 调用。

大规模测量控制器队列时间、执行节点 CPU 和内存、网络吞吐量、目标连接限制、API 限制、机密提供程序延迟和日志量。在不验证目标和 API 容量的情况下增加分叉可能会降低自动化服务的可靠性。

## 采用清单

- [ ] 向所有者注册每个生产仓库、角色、集合、计划、凭证和作业。
- [ ] 定义支持的 Ansible、Python、集合、操作系统和云提供商版本。
- [ ] 固定依赖关系并构建经过批准的执行环境。
- [ ] 保护分支并需要适当的平台、安全性或工作负载审核员。
- [ ] 向 CI 添加语法、lint、依赖项、机密和安全检查。
- [ ] 添加有效、无效、未更改、失败和幂等测试。
- [ ] 从代码、清单、变量、日志和制品中删除机密。
- [ ] 配置最小权限目标和云身份并进行生产分离。
- [ ] 将生产作业绑定到批准的清单、凭证、Playbook 和输入模式。
- [ ] 设置有界并发、金丝雀行为、停止条件和 Operator 取消。
- [ ] 添加预检查、更改后验证、回滚或前向恢复指导。
- [ ] 发布工作证据并将其与变更、事件或请求日志记录相关联。
- [ ] 测试清单源故障、凭证故障、部分执行和恢复。
- [ ] 安排偏差评估并分配修复所有权。
## 治理、例外和执行

云卓越中心负责该标准。平台工程运营共享自动化服务。工作负载、安全、网络、数据库、应用、可靠性和 IT 运营团队负责其范围内的控制。

例外情况 MUST 满足以下条件：

1. 识别未满足的需求 ID；
2. 描述业务合理性和量化风险；
3. 定义补偿控制和额外监控；
4.指定负责人和技术审批人；
5. 包含不超过180天的有效期；和
6. 定义临时异常的迁移或修复计划。

过期的例外是不合规的。自动检查 SHOULD 阻止新的不合规版本，并在修复积压中跟踪现有差距的严重性、所有者、到期日期和证据。

平台团队应集中执行仓库检查、批准的执行环境、控制器 RBAC、清单和凭证分离以及证据保留。工作负载团队仍然对特定于目标的配置和服务验证的正确性负责。

## 审核周期

至少每年审查一次此标准，并在 Ansible、控制器功能、身份、安全要求、法规或自动化操作模型发生重大变化之后审查此标准。当控制意图未更改时保留需求标识符。
